# SalesSetu public Gmail release checklist (prepared, not submitted)

**Current implementation:** Google sign-in uses a frontend Auth.js client with `openid email profile`. **Connect Gmail** uses a separate backend OAuth client and asks for `openid email https://www.googleapis.com/auth/gmail.send`. The backend callback is `https://sales-setu-seven.vercel.app/api/gmail/oauth/callback`; the localhost callback is `http://localhost:5000/api/gmail/oauth/callback`. The callback uses a one-use state bound to the initiating workspace. Refresh/access tokens are encrypted under that workspace in PostgreSQL. Disconnect removes the local token and attempts revocation. The exact production OAuth client, consent publishing state, authorized domains, and Console redirect list **cannot be confirmed from this checkout**; verify them in Google Cloud and Vercel without copying secrets to chat or Git.

## Google Cloud Console, Gmail OAuth project

1. Keep the Gmail OAuth project/client separate from the basic-identity sign-in project/client. In Google Auth Platform → **Audience**, choose **External**. Testing restricts access to listed test users. When ready, change publishing status to **In production**; this is a Console action, not an app-code switch. Do not do this until the review material and domains are ready.
2. In **Branding**, set the accurate SalesSetu app name, logo if used, operator-owned support email, developer contact, public homepage, `/privacy`, and `/terms`. Publish the reviewed pages on the verified domain. Add/verify its authorized domain through Search Console. Keep branding aligned with the deployed app.
3. In **Clients**, find the Web OAuth client whose ID equals backend Production `GMAIL_OAUTH_CLIENT_ID` (compare privately). Register the exact Production callback `https://sales-setu-seven.vercel.app/api/gmail/oauth/callback` if using the present backend origin; keep the local callback on the development client. Backend Production `GMAIL_OAUTH_REDIRECT_URI` must match its registered redirect byte for byte. Frontend Google identity redirect `https://salessetu-web.vercel.app/api/auth/callback/google` belongs to the *identity* client, not this one.
4. In **Data Access**, declare only the scopes actually requested: `openid`, `email`, and `https://www.googleapis.com/auth/gmail.send`. `gmail.send` is **sensitive**. It permits sending on behalf of a user; SalesSetu does not need inbox read/modify scopes. Give this justification: “After a user separately connects Gmail, SalesSetu sends only that user's explicitly approved, current-revision outreach or follow-up to a confirmed recipient. The user previews and confirms each send. The app does not read mailbox contents or send automatically.”
5. Submit the sensitive-scope review when the project and pages are ready. Record a demonstration that shows: sign in; Integrations → Connect Gmail; the English consent screen with the correct app name/client ID/scopes; connected sender; draft; confirmed recipient; current-revision approval; preview; explicit send to an address you control; and the resulting sent record. Use a stubbed or controlled test account for other providers. Upload the video as unlisted and provide its URL in Google's review form. Include a reviewer account/instructions if requested. **No demonstration email was sent during preparation.**
6. Track Google's Verification Center and respond to reviewer requests. Publishing alone does not approve a sensitive scope. Until verified, users may see an unverified-app warning and a 100-new-user cap; Testing has a test-user allowlist. A Google Workspace administrator may block the OAuth app regardless of its publishing state. Do not claim code can lift these restrictions.

Google references: [Gmail scope classification](https://developers.google.com/workspace/gmail/api/auth/scopes), [sensitive-scope verification and video](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification), [Audience/testing and caps](https://support.google.com/cloud/answer/15549945), [OAuth production policy](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance).

## Apollo is a separate licensing decision

Apollo People Enrichment accepts an API key scoped to `api/v1/people/match`; a Master key is unnecessary. For the isolated local workspace launcher, add backend-only `APOLLO_API_KEY` to the ignored `backend/.env.phase1.local` and restart that backend. A direct `npm run dev` instead loads `backend/.env` through `dotenv/config`; use the file your launcher actually loads. Do not copy the key to the frontend. SalesSetu calls Apollo only after a selected-POC **Find work email** action; it requests no personal email, phone, or waterfall enrichment. No Apollo credential is configured by this document.

Apollo's standard [API terms](https://www.apollo.io/terms/api) grant internal-business-use access and restrict third-party product integration without Apollo approval. [Apollo's guidance for customer integrations](https://knowledge.apollo.io/hc/en-us/articles/4416173158541-Use-Apollo-API) recommends OAuth for mutual Apollo users; sharing Apollo data with non-Apollo users can require a custom contract. **Do not use an internal-use key to provide enrichment to arbitrary SalesSetu customers without Apollo's written permission or a suitable agreement.** Production rejects lookup unless `APOLLO_CUSTOMER_USE_ENABLED=true` is set after that license is confirmed. Keep this flag false until then. Manual recipient entry remains available.
